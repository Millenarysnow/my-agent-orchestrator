# Fork 应用更新总开关

本文规定 fork 构建如何暂停应用自身的更新与安装包回退下载，并保留以后接入自有分发源的能力。桌面发布与安装包约束见 [desktop-release.md](../../frontend/docs/desktop-release.md)；本地项目与远端的边界见 [本地项目基线与远端解耦.md](本地项目基线与远端解耦.md)。

## 目标与非目标

**当前 fork 构建默认关闭应用更新能力。** 启动、后台定时任务、设置页操作、功能预览版本选择和 CLI 缺少桌面程序时的回退，都不得检查或下载原项目的新版本，也不得安装已缓存的应用更新。fork 已经独立开发，原项目的新版本不能替换本地功能。

**保留已有更新实现和用户偏好。** 以后确认分发源后，只需调整构建策略并重新构建，即可重新使用现有检查、下载、渠道选择和安装流程。关闭能力不清空用户的 `update-settings.json`，也不删除下载缓存或用户数据。

**本方案仅约束 AO 应用自身的分发。** agent、模型、浏览器运行时等依赖的安装更新，以及用户项目的 Git、PR 和其他联网能力，保持各自的授权与生命周期。自建更新服务器、发行品牌和签名体系不在此次实现范围内。

## 核心方案

**以一个受版本控制的布尔值决定当前构建是否提供应用更新能力。** 唯一来源是 `backend/internal/buildpolicy/app-updates.json` 中的 `enabled`，当前为 `false`。Go 通过嵌入读取，Electron 主进程和 renderer 通过共享模块导入同一文件；不分别维护 Go 和 TypeScript 常量，避免其中一端重新访问原分发源。

**总开关高于用户偏好。** `UpdateSettings.enabled` 仍只表达自动下载偏好；它原本不关闭启动检查和周期检查，不能复用为构建策略。旧偏好中的 `enabled: true`、nightly 或 feature pin 都不能越过总开关。

**开关只在构建后生效，不提供运行时热切换或环境变量强制开启。** 这样启动时即可确定能力，不需要处理运行中切换导致的下载取消、已排队操作和界面状态竞态。无效策略不能被解释为开启。

## 结构与依赖边界

**`buildpolicy` 只提供构建能力，不能读取用户状态或访问网络。** 它不依赖 CLI、daemon、Electron 或发布服务；否则一个下载决策会反向引入应用生命周期或运行环境依赖。

**`auto-updater.ts` 负责执行层的拦截，`main.ts` 负责跳过启动引导。** 只跳过 `initAutoUpdates` 会遗漏 IPC 直接调用的手动检查、设置写入后的定时器重建和安装入口。更新模块必须在恢复暂存状态、注册更新事件或调度检查之前判定总开关。

**`feature-builds.ts` 的远端发现同样受总开关约束。** 列出预览版本、核对固定 PR 是否退休都属于应用更新发现；只隐藏选择器仍会让其他调用者访问 GitHub。读取当前安装版本的本地信息可以保留。

**`checkDesktopVersionFloor` 也服从总开关。** 它独立读取上游的最低支持版本，可能提示下载并强制退出；关闭 `auto-updater.ts` 不会关闭这条路径。fork 的可用性不能由上游的版本要求决定，必须在 fetch、对话框和退出重试计时器之前结束。

**`UpdatesSection` 展示能力状态，不能成为唯一拦截层。** 主进程才拥有下载与安装权限。界面保留当前版本，禁用更新操作和渠道设置，并明确说明当前构建已禁用应用更新，避免把构建限制显示成网络错误。

**CLI 在应用包下载边界判定同一策略。** `ao start` 仍解析并启动已有本地桌面程序；找不到时返回明确错误，要求安装 fork 的桌面包，不执行 `fetchApp` 的平台下载实现。已有本地安装的启动不以总开关开启为前提。

## 关闭时的行为约定

**后台更新完全不启动。** 不显示首次运行的更新偏好对话框，不启动检查、功能预览版本退休轮询或更新提醒计时器，不因读取旧设置而恢复这些任务。

**手动入口返回稳定的不可用状态。** 复用已有 `unsupported` 更新状态及请求关联信息，说明应用更新已被当前构建禁用。检查、下载、返回主渠道和安装均在产生更新副作用之前结束，不能把操作静默转交给原分发源。

**已缓存的更新不能在退出时安装。** 关闭时显式禁用 `autoDownload` 和 `autoInstallOnAppQuit`，不恢复 `staged-update.json`，并拦截主动安装。仅停止检查无法覆盖此前下载或记忆的更新。

**用户偏好保持原样。** 关闭时的界面不允许修改更新偏好；即使绕过界面调用设置写入，也不启动更新任务。保留旧设置是为了以后重新启用时恢复原有意图，不代表该设置在关闭期间生效。

## 必须守住的约束与陷阱

**构建策略必须包含在 Electron 与 Go 的产物中。** 不在运行时按工作目录读取 JSON；安装目录和 CLI 调用目录可以不同，丢失配置若回退为开启会重新连接原更新源。

**策略 JSON 同时属于 Go 和 Electron 的构建输入。** CI 的变更选择必须触发两端验证；只按文件所在的 backend 目录选择测试，会让以后单独切换总开关时漏掉前端验证。

**打包生成的更新源配置不能用作总开关。** `forge.config.ts` 会在打包时重写 `app-update.yml`；只改该文件不能持续生效，删除文件又会把“已禁用”变成更新器错误。

**关闭能力不重构原有渠道与安装逻辑。** 这些流程包含版本比较、原生暂存和退出策略；用构建入口包住它们可以保留以后重新启用的行为，删除或散改内部状态机会增加恢复成本。

## 被否决的方案

**仅关闭设置里的自动更新被否决。** 现有实现仍在启动和约每 15 分钟检查版本，手动更新及部分暂存恢复路径也仍可下载。

**仅隐藏按钮或跳过启动函数被否决。** IPC、设置写入、预览版本发现和 CLI 回退下载仍能绕过界面或启动入口。

**用无效地址阻断请求被否决。** 程序仍然重试、产生错误并运行更新状态机，且难以区分主动禁用与服务故障。

## 重新启用与扩展准入

**启用总开关之前，必须先确认产物携带 fork 自己的更新源。** 现有 `AO_RELEASE_REPO` 可指定 GitHub Releases，但 CLI 的 `releaseRepo` 和 `desktop-version-floor.ts` 的版本要求及下载地址也必须一起切换；否则桌面升级、首次安装和强制升级提示会来自不同来源。

**接入自有 HTTP 更新服务器需要单独设计 provider。** 当前稳定版说明、nightly 和 feature pin 都含 GitHub 专用发现逻辑；不能仅把一个地址改成服务器 URL 后宣称完成迁移。新 provider 必须继续服从此总开关，且不得在配置失效时回退到原项目。
