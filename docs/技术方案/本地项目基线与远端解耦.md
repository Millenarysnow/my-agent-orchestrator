# 本地项目基线与远端解耦

本文规定本地项目如何选择任务起点，以及本地工作与远端能力的依赖边界。适用于单仓库项目和多仓库工作区；会话生命周期与存储边界见 [architecture.md](../architecture.md)。

## 目标与非目标

**本地项目可以完全依靠已有 Git 分支和提交运行。** 注册项目、创建任务、恢复工作区和查看本地差异，不以配置 `origin`、登录 GitHub、访问远端或推送提交为前提。远端不可达不应改变任务起点，也不应增加启动等待。

**继续为任务创建独立分支和 worktree。** 本方案解除远端依赖，保留任务之间的文件隔离；不让多个任务共同修改源目录的 checkout，不自动搬运源目录未提交的文件。

**克隆、PR/MR、CI 和云项目保留各自的远端语义。** 用户主动使用这些能力时可以访问相应服务；它们不能反向成为普通本地任务的准备条件。本方案不新增通用同步或发布界面。

## 核心方案

**创建本地项目时，从本地分支列表选择项目基线；每个任务从该分支当时的提交创建独立 worktree。** 项目基线指持续使用的分支，任务起点指本次创建时解析出的不可变提交。区分两者可以同时保留本地后续提交和创建期间的一致性。

**所有必要 Git 操作由 daemon 完成。** renderer 只展示选项并提交选择；分支来源、有效性、创建起点和恢复依据由后端解释，避免桌面本机与已连接主机出现不同规则。

## 项目基线的选择与保存

**分支选项只来自所选仓库的 `refs/heads/*`。** 远端跟踪引用和 tag 不混入选项；读取选项不执行远端探测。默认选中源目录当前检出的本地分支，其他本地分支由用户选择。

**保存明确的本地引用，而不是有歧义的短名称。** `ProjectConfig.DefaultBranch` 可以承载 `refs/heads/<name>`；界面显示短名称。否则同名 `origin/<name>` 或恰好与远端同名的分支前缀会改变实际起点。

**选择基线不切换源目录的 checkout。** 源目录正在做的工作和后续任务的基线分别属于用户控制的状态，不能互相覆盖。

**基线分支必须存在并指向提交。** detached HEAD 不妨碍选择其他已有本地分支；没有可选分支或尚无提交时，先完成明确授权的本地初始化和首次提交。空列表不能隐式触发创建远端。

**项目设置可以调整基线，调整只影响以后创建的任务。** 已存在任务继续使用自己的分支和已记录的比较依据；基线被删除时，新任务提示重新选择，不偷偷改用其他分支。

**旧项目的兼容处理只读取本地状态。** 已配置的本地分支优先于同名远端跟踪引用；旧配置中明确指定的远端引用可以继续使用本地缓存，但不自动刷新。`auto` 在本地解析默认元数据，找不到时使用源目录的当前本地分支；新项目注册时将实际选择保存为明确本地引用，避免长期跟随源目录的临时切换。

## 本地导入与多仓库工作区

**缺少远端不属于 Git 未就绪。** `importer.Validate` 的必做准备仅包括本地初始化和首次提交；检查结果可以展示是否有远端，但该信息不能禁用继续操作。

**本地导入不得隐式创建 GitHub 仓库或推送。** 远端配置和发布只有在对应能力被明确选择并授权时才发生。批准本地初始化不等于批准远端创建或推送。

**多仓库工作区的子仓库有本地提交和可解析基线即可参与任务。** `prepareWorkspaceProject` 和 `validateWorkspaceChild` 不再以存在 `origin` 判断就绪。根仓库和各子仓库独立解析基线，不能把根仓库的分支名强加给所有子仓库。

**项目类型不能由是否存在远端决定。** 单仓库与多仓库的区别是用户选择的组织方式和目录中的仓库结构；添加或删除 `origin` 不应把同一目录变成另一种项目。

## 任务创建与提前准备

**Chat、TUI、编排器和提前准备共用同一本地基线规则。** `session_manager` 在创建工作区前解析本地基线，不再调用自动 fetch 流程；`gitworktree` 的后备解析也不能重新访问远端。只删除外层刷新会遗漏适配器里的隐式 fetch。

**创建 worktree 使用解析出的提交 SHA。** 基线引用用于解释来源和后续比较，SHA 用于固定本次起点。不能让创建命令再次按短分支名解析，否则并发提交或引用歧义会使记录与实际文件不一致。

**提前准备的工作区必须与正式启动时的基线相符。** `task_preparation` 已经提前创建分支和文件，正式启动不能只凭 token 复用；项目基线或对应提交变化时，丢弃旧准备并按当前基线创建。清理仍遵守原有分支初始提交和脏文件保护，不借失效处理删除用户工作。

**任务的新分支名与项目基线是两件事。** 显式任务分支的恢复和已有远端任务分支缓存需要独立处理，不能让同名远端任务分支覆盖用户为新任务选中的本地起点。

## 恢复与文件差异

**恢复已有任务优先重接原工作区和原任务分支。** 缺失目录可以从仍存在的任务分支恢复；不能通过更新项目基线重新生成一个看似恢复成功、实际丢失任务提交的工作区。

**原任务分支和提交均不可用时，明确报告不可恢复。** 远端重新获取属于单独的恢复动作，不是普通恢复的隐式后备；也不能从当前项目默认分支伪造任务历史。

**本地文件差异使用记录的明确基线和提交。** 创建、恢复、文件查看与分支状态不能各自按 `origin/<name>` 重解释同一个本地基线，否则会把已有本地提交算成新任务修改。基线引用失效时保留已记录提交作为后备；PR 视图继续使用 PR 自身的比较语义。

## 结构与依赖边界

**导入服务提供本地分支选择所需的事实，项目服务验证并保存选择。** 关键边界是 `service/importer`、`service/project` 和 `ProjectConfig`。分支列表通过已有 daemon API 返回，HTTP 合约和前端类型随源代码重新生成。

**工作区适配器拥有 Git 引用解析与 worktree 物化。** `gitdefault` 区分本地检查与主动远端解析，`adapters/workspace/gitworktree` 不把远端解析用于本地生命周期。`session_manager` 负责准备工作区的复用和失效，不把这些规则移入 renderer。

**远端凭据和配置不会授权发布。** 普通自由任务保持已有发布权限边界；provider issue 或 PR 的专用工作流继续服从用户的本地限定。无远端项目不能收到必须 push 或创建 PR 的无条件指令。

## 必须守住的约束与陷阱

**Git worktree 共享对象库、分支和仓库配置。** 为满足本地创建而自动添加远端、改写源分支或 reset，会影响用户原 checkout；本方案只建立独立任务分支，不修改原分支历史。

**本地缓存的远端引用不代表已发生联网。** 本地读取 `refs/remotes/*` 可用于兼容已有配置和 PR 元数据；禁止的是为本地流程隐式刷新这些引用，以及用它们覆盖明确选择的本地引用。

**源目录未提交文件不包含在分支提交中。** worktree 从提交创建，因此不会自动继承这些文件；自动提交、stash 或复制它们会扩大授权范围并改变用户工作状态。

**保护数据的约束不随远端解耦放宽。** 脏 worktree、未知占用目录、已产生额外提交的准备分支仍然不能被强制删除；失效与取消不是删除用户工作的授权。

## 被否决的方案

**只增加“跳过 fetch”开关不足以完成目标。** 自动解析、预创建和恢复仍能绕过外层开关访问远端，而且同名远端引用仍可能胜出。

**自动使用远端默认分支违背本地选择。** 远端的 main 可以与用户的版本维护分支不同，网络可用性也不应决定本地任务从哪份代码开始。

**每次任务都跟随源目录当前 checkout 不作为新项目默认。** 创建项目时的选择必须持续生效，否则用户为检查其他分支而切换目录，会意外改变以后任务的基线。

**永久固定项目创建时的提交不能代替分支选择。** 用户向基线分支新增的本地提交应进入后续任务，只有单次任务起点需要固定 SHA。

## 扩展准入

**未来增加同步、远端绑定或发布入口时，必须保持本地流程独立。** 同步后的提交可以影响后续任务，但已创建任务不能被后台更新重置；后台 SCM 观察失败也不能阻止本地操作。

**多仓库逐仓库的可视化基线编辑可后续扩展。** 本次保留每个子仓库独立的明确本地基线；任何编辑界面都必须使用该子仓库自己的本地分支列表，不能用远端列表或根仓库列表代替。
